---
name: tool-eval
description: Evaluate engine tooling, public tools, libraries, languages, and build-vs-buy options before creating custom game-development tools
---
1. Define the user workflow, required capabilities, constraints, data formats, and success criteria.
2. Check existing project scripts, skills, and built-in engine functionality first.
3. Consider engine plugins, maintained open-source libraries, standalone editors, CLI utilities, other languages, and custom or hybrid approaches.
4. For each viable option, compare functional fit, version/platform compatibility, integration effort, maintenance, license/cost, data portability, automation, performance, and team workflow.
5. Verify current capabilities, license, and compatibility using available primary sources; mark unverified claims. Never invent integrations or pricing.
6. Present concise evidence-linked comparison, recommendation, rejected options, and proof-of-concept/validation plan. Example: evaluate MagicaVoxel/Blockbench/Blender before writing a voxel editor; evaluate narrative tools before writing a VN editor.
7. Request approval before installation, custom implementation, or other modifications. Document accepted decisions in DECISIONS.md and dependencies in ARCHITECTURE.md when relevant.
8. Revisit decisions only when requirements or evidence materially change; don't repeatedly pitch rejected options.
